Every layer holds these 14 tensors; the only others are `model.embed_tokens.weight`, `model.norm.weight` and a separate `lm_head.weight` (`tie_word_embeddings` is false). `beta` and `eps` are 0-d (shape `[]`), so they load with an empty shape, not `[1]`.

**1. The stored `alpha_p`/`alpha_n` are raw values that overflow a naive `softplus`.** transformers applies `softplus` in the forward pass, as `softplus(alpha_p)` and `beta + softplus(alpha_n)`. In both 8B models (base and Instruct), the raw `alpha_p` of layers 0, 1 and 2 is 166, 174 and 128, above the point where `exp` overflows in f32 or bf16 (≈ 88.7). PyTorch's `softplus` returns `x` itself above its default threshold of 20, so transformers' Python path is unaffected, but candle has no shared `softplus`, and every model that needs one writes `(x.exp()? + 1.0)?.log()` (links in the table below). On those values, plus two in-range ones (layers 9 and 14), candle 0.11.0 gives:

```
F32  naive softplus [166.0, 174.0, 0.98828, -0.01514] -> [inf, inf, 1.3047072, 0.6856058]
BF16 naive softplus [166.0, 174.0, 0.98828, -0.01514] -> [inf, inf, 1.3046875, 0.68359375]
```

xIELU would then return `inf` for every positive input in those layers (its `x > 0` branch is `alpha_p * x * x + beta * x`). In f32/bf16 the 70B (largest raw value 11.1) and the v1.1 1.5B (32) stay in range, so a port tested on those alone would look correct. In f16, whose `exp` overflows above ≈ 11.09, the naive form also breaks the 1.5B (layers 1 and 2), the 70B (layer 1) and more layers of the 8B. Since these scalars are constants at inference, computing the effective `alpha_p` and `alpha_n` once at load time, on the host and with a threshold as PyTorch does, avoids it in every dtype. This also bears on your question 2: an xIELU in `candle-nn` would need to take the raw parameters and apply a thresholded `softplus`, or document that it expects the effective values.

**2. The v1.1 1.5B config can't be read by `llama.rs`'s RoPE types.** The three 2509 models use `llama3` scaling (`rope_theta` 12 000 000, 65 536 positions), which candle's `llama.rs` implements. `swiss-ai/Apertus-v1.1-1.5B-Instruct` has `"rope_scaling": {"rope_type": "default"}`, `rope_theta` 500 000, 4096 positions and a head dim of 64. `Llama3RopeConfig` requires `factor` and the other scaling fields, so with candle-transformers 0.11.0, deserializing that config as `LlamaConfig` fails with ``missing field `factor` ``. A port that reuses those types would need the scaling fields optional, or its own config type.

**3. `beta` and `eps` are the same in every layer** of all four checkpoints: 0.5 and −9.98e−7, which is −1e−6 rounded to bf16. transformers' fused CUDA path uses the constructor defaults (0.5 and −1e−6) instead of the buffers, so reading them from the checkpoint and using constants agree, up to the bf16 rounding of `eps`.

I couldn't check Apertus 1.5: `swiss-ai/Apertus-v1.5-8B` is gated and my token hasn't accepted its license.
