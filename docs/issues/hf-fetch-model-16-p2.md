This issue was closed automatically by my own commit [`3667323`](https://github.com/mi-for-the-rust-of-us/hf-fetch-model/commit/3667323142aa994d8dd6a97748d5ce02dc262f06), whose message said "Closes #16". That keyword closes an issue as soon as the commit reaches `main`, so it closed this one as completed, with no explanation, while only part of it was done. Here is where it actually stands.

**Fixed: suggested fixes 1 and 4.** The fix is on `main` and not yet released. `du`, `du --tree`, `du --json`, `status`, `cache gc` and `cache delete` count every physical file under `blobs/` and `snapshots/` once, in [`walk_repo_files`](https://github.com/mi-for-the-rust-of-us/hf-fetch-model/blob/3667323142aa994d8dd6a97748d5ce02dc262f06/src/cache.rs#L1019). It walks `blobs/` first, recording each blob's identity, then `snapshots/`. A snapshot entry that is a symlink adds no bytes of its own, and on Unix a hard link to an already-counted blob adds none either. The single-repo view in the example above, `du <repo>`, took a second commit, [`e5949c7`](https://github.com/mi-for-the-rust-of-us/hf-fetch-model/commit/e5949c7a39cc60d5819c659c431a7220d96f788b): the first fix left its total adding up only its per-file listing, which for the example above still meant 5.18 GiB for a 10.36 GiB directory. Measured today on the machine this was filed from, against the counting script in the issue above:

| | GiB |
|---|---:|
| `du` before the fix (snapshot files only) | 630.98 |
| under `blobs/`, previously uncounted | 184.07 |
| **`du` after the fix** | **815.06** |
| **bytes on disk (the script above)** | **815.06** |

That last match is exact: all 75 repos agree byte for byte, 875,158,823,198 bytes on each side. The figures are lower than the ones above by exactly one repo: the issue's own example, `distaste447/zeta-2.1-NVFP-GGUF`, has since been deleted, taking its 5.18 GiB blob and its 5.18 GiB copy with it. The "before" row needs no old binary: the script found no symlinks and no hard links here, so the old snapshot-only total is exactly the sum of the files under `snapshots/`.

`cache gc --size` was the open question in the issue. It does budget against this same figure ([`compute_gc_plan`](https://github.com/mi-for-the-rust-of-us/hf-fetch-model/blob/ee05204dcf04136a7b425c9cec37bfa43cddada8/src/bin/main.rs#L4768) sums the per-repo totals, and its `Freed` line adds the same sizes), so before the fix it planned and reported against too small a number. It now uses bytes on disk, as does the `cache delete` preview and its `Freed ...` line.

**A correction to the issue itself.** Under suggested fix 1 I wrote: "Totals on the usual Unix layout are unchanged." That is wrong, and the Unix layout was actually the *worse* case. The old walk read each size from `DirEntry::metadata` ([`cache.rs:977` at `c9b9179`](https://github.com/mi-for-the-rust-of-us/hf-fetch-model/blob/c9b9179c4c3701ec2a6bf9c541823f483b1f6f34/src/cache.rs#L977)), which `std` documents as equivalent to `symlink_metadata`. So where a snapshot entry is a symlink into `blobs/`, it returned the length of the link's *target path*, not the file's size, and it still never counted the blob. Running the pre-fix code on Linux, a 1 MB file reported **20 bytes**, the length of `../../blobs/deadbeef`. A symlinked cache therefore reported almost nothing at all. The Windows copy layout this issue came from was the milder of the two.

The same mistake appeared in two more places, neither mentioned above, both fixed in the same commit:

- **`inspect --list`'s per-file sizes**, which come from the public `inspect::list_cached_tensor_files` / `list_cached_safetensors`. On a symlinked cache these listed every tensor file at a few dozen bytes.
- **The summary line printed after a download.** On Linux it reported 7 bytes for a 1 MB download, or nothing at all, since it is skipped when the total is 0.

All three now go through one helper, [`cache::resolved_file_size`](https://github.com/mi-for-the-rust-of-us/hf-fetch-model/blob/3667323142aa994d8dd6a97748d5ce02dc262f06/src/cache.rs#L934). Seventeen tests came with the fix: nine that run everywhere, and eight Unix-only ones covering symlinked, hard-linked and dangling pointers, plus a symlink *inside* `blobs/`, which is not followed, so a crafted cache can't charge a repo for bytes outside it. The Unix-only tests were run on Linux. Built against the pre-fix code instead, a harness of the accounting cases fails 7 of 8 (the hard-link case passes on the old code by coincidence), and the symlink cases for `inspect --list` and the download summary fail too.

One deliberate exclusion: hf-fm's own `.hf-fm-header-cache/` sidecar (written only by `inspect --cache-headers`) sits beside `blobs/` and `snapshots/` and is not counted. There is none in this cache, so it costs 0 bytes above. Since nothing prunes it, it is being looked at separately.

**Not fixed: suggested fixes 2 and 3**, the two that would actually give the disk back: hard-linking a snapshot entry to its blob instead of copying it, and reclaiming the copies that already exist. `du` now shows the duplication honestly, but it doesn't free any of it. Both move to #21. Fixing this turned up one constraint they will have to deal with. On Windows, `std` can only tell whether two paths are the same file through an unstable API, and the only other route is an `unsafe` Win32 call, which this crate forbids. So the accounting above recognises hard links on Unix only. That is correct today, because nothing in the stack creates a hard link: hf-fm's [`symlink_or_copy`](https://github.com/mi-for-the-rust-of-us/hf-fetch-model/blob/ee05204dcf04136a7b425c9cec37bfa43cddada8/src/chunked.rs#L1044) and `hf-hub`'s own pointer writer each either symlink or copy. Fix 2 would change that, so it has to come with a way to recognise hard links on Windows, or `du` would start counting them twice.
