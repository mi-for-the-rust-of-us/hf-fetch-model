The block size is 64 tokens off Metal (`config.rs` L473). The log's "[1 seqs x 786432 tokens]" and "24k bytes per token" give ⌈786,432 / 64⌉ = 12,288 blocks and 786,432 × 24 KiB = 18.00 GiB, both exactly as logged. **Which mode ran is inferred, not read:** the reporter wrote that the length was "provided by yarn scaled RoPE", which does not say whether `max_model_len` was passed. With `max_model_len` set, the pool is exactly `max_num_seqs` sequences' worth by construction; in the auto mode (`auto_decide_params`, L544-L591), `num_gpu_blocks` is all of free × `kv_fraction` divided by the block size, and the context length is then fitted inside it, so a pool of exactly one 786,432-token sequence (12,288 blocks, no remainder) would be a coincidence of free memory. @ivarflakstad, since those numbers came from my earlier [reply](https://github.com/huggingface/candle/issues/3530#issuecomment-4441304624), three notes that may help decide, without answering for @sempervictus:

**1. The model-size figure still holds, with the same caveat.** Re-running `hf-fm inspect nvidia/Qwen3-Next-80B-A3B-Instruct-NVFP4 --dtypes` today gives the same four rows (U8 36.26 GiB, BF16 6.45 GiB, F8_E4M3 4.53 GiB, F32 577.6 KiB), 47.24 GiB across 11 shards. It is still a guess at the model from the crash log; the reporter hasn't named it.

**2. The ~14 GiB "runtime / RSS overhead" is a remainder, not a measurement.** It is what is left of `used` after subtracting the weights, the KV pool and the Mamba state: 13.70 GiB as I computed it (81 − 47.24 − 18.00 − 2.06), and between 13.49 and 14.79 GiB depending on whether one takes the rounded `free -g` figure or the crash-time `free -m` (84,061 MiB), and the Mamba budget from the allocation line (2.06 GiB) or from the later scheduler line (2.27 GiB). It lumps together everything not itemized (CUDA context, workspaces, allocator slack), so I wouldn't read an inefficiency into it without measuring the process directly.

**3. The 18 GiB KV pool is the configured context, sized by the engine on top of candle.** The backtrace's `vllm_rs` is vllm.rs, since renamed [xinfer](https://github.com/guoqingbao/xinfer) ([#354](https://github.com/guoqingbao/xinfer/pull/354)). The reporter's log lines match its source at [`cf9b63b`](https://github.com/guoqingbao/xinfer/tree/cf9b63be99715ae1003471bf0e21c4bdb3f7aad9) (2026-05-05) exactly, the last version whose refusal reads "your prompt requires … new tokens", so that is the code I read:

- The pool holds exactly one sequence of `max_model_len`: the log's `scheduling limits [1 seqs x 786432 tokens]` and its 12,288 GPU blocks agree to the block (64 tokens each), and at 24 KiB (24,576 bytes) a token that is 19,327,352,832 bytes, the log's "18.00 GB" (the engine's GB is 2³⁰ bytes, so 18.00 GiB). That is what the allocator produces by construction when `max_model_len` is set: it [sizes the pool to what `max_num_seqs` sequences of `max_model_len` tokens need](https://github.com/guoqingbao/xinfer/blob/cf9b63be99715ae1003471bf0e21c4bdb3f7aad9/src/utils/kvcache_allocator.rs#L615-L636), and free memory (`cuMemGetInfo_v2` × [`kv_fraction`, 0.95 in that mode](https://github.com/guoqingbao/xinfer/blob/cf9b63be99715ae1003471bf0e21c4bdb3f7aad9/src/utils/kvcache_allocator.rs#L309-L313)) only caps it. Left to size itself, it would take all of free × `kv_fraction` instead, and the block count would be whatever that gives. So the ~38 GiB left free is not memory the allocator failed to claim; in this mode it doesn't try to.
- The refusal is a `candle_core::bail!` in the engine's own [request admission](https://github.com/guoqingbao/xinfer/blob/cf9b63be99715ae1003471bf0e21c4bdb3f7aad9/src/core/engine.rs#L610-L618), which is why `candle_core::error::Error::bt` appears in the trace: candle supplies the error type. At that moment 416,192 of the pool's 786,432 tokens were free, so 370,240 were held, and the request needed 524,288.

What this doesn't explain is why the same conversation works with the 35B sibling, or on SM120; the 35B run's `KVCache Allocation` line would show whether it was configured differently. Either way, the pool's size comes from the engine's configuration, not from how candle maps the model, so closing here and taking any remaining question to xinfer seems reasonable to me, unless @sempervictus has seen the gap with candle alone.
