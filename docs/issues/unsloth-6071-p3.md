Following up on @danielhanchen's "worth raising upstream with the failing file": I went to do that, and found the upstream fix had already landed **before this issue was filed**. Posting the bisect so nobody files a duplicate.

**Root cause: a stale `llama.cpp` build, not an export bug.**

Before commit [`2555826`](https://github.com/ggml-org/llama.cpp/commit/255582687b8dd211fdbc582e43ab842491554e94) ("llama + spec: MTP Support", PR [#22673](https://github.com/ggml-org/llama.cpp/pull/22673), merged 2026-05-16), [`src/models/qwen35.cpp:19-21`](https://github.com/ggml-org/llama.cpp/blob/b81c2cdd748dc2704d5989cf03936325554c12d3/src/models/qwen35.cpp#L19-L21) marked recurrent layers like this:

```cpp
        for (uint32_t i = 0; i < hparams.n_layer; ++i) {
            hparams.recurrent_layer_arr[i] = ((i + 1) % full_attn_interval != 0);
        }
```

For a 9B MTP file (`block_count=33`, `nextn_predict_layers=1`), `n_layer` is 33, so `i = 32` evaluates `(32 + 1) % 4 == 1 != 0` and **layer 32 is flagged recurrent**. The loader then demands `blk.32.ssm_conv1d.weight` from a block that is the NextN speculative-decoding head, which carries `attn_*`/`ffn_*`/`nextn.*` and no SSM tensors by design. That is precisely the reported error.

PR [#22673](https://github.com/ggml-org/llama.cpp/pull/22673) added the `n_main` guard, at [`qwen35.cpp:22-26`](https://github.com/ggml-org/llama.cpp/blob/255582687b8dd211fdbc582e43ab842491554e94/src/models/qwen35.cpp#L22-L26):

```cpp
        const uint32_t n_main = hparams.n_layer - hparams.nextn_predict_layers;
        uint32_t full_attn_interval = 4;
        ml.get_key(LLM_KV_FULL_ATTENTION_INTERVAL, full_attn_interval, false);
        for (uint32_t i = 0; i < hparams.n_layer; ++i) {
            hparams.recurrent_layer_arr[i] = (i < n_main) && ((i + 1) % full_attn_interval != 0);
```

For the 9B MTP file `n_main` is `33 - 1 = 32`, so at `i = 32` the new `i < n_main` test is `32 < 32`, which is false. The NextN head is no longer flagged recurrent, and the same PR routes it to a dedicated `load_block_mtp` path instead. That guard is still on master as of 2026-09-16, as [`is_recr_impl[i] = (i < hparams.n_layer()) && …`](https://github.com/ggml-org/llama.cpp/blob/0bec16e3880a148a7fc3887cdf71f81c547aff7a/src/models/qwen35.cpp#L21).

Being precise about the evidence: the single load log in this issue is a two-line paste under a heading covering all four sizes, and the report attributes `blk.32.ssm_conv1d.weight` to the 4B as well as the 9B-MTP, so there is no 9B-specific log in this thread. The only crash log with a real file path is dakotahp's.

It does **not** account for the other three. `Qwen3.5-0.8B-GGUF` (`block_count=24`), `Qwen3.5-4B-GGUF` (32) and `Qwen3.5-35B-A3B-GGUF` (40) carry no NextN head, so `nextn_predict_layers` is 0, `n_main == n_layer`, and the pre-fix line above behaves identically to the fixed one. (The 35B-A3B is the separate `qwen35moe` architecture; its own [`qwen35moe.cpp`](https://github.com/ggml-org/llama.cpp/blob/b81c2cdd748dc2704d5989cf03936325554c12d3/src/models/qwen35moe.cpp#L23) carried the identical loop and was patched by the same PR.) The tensor loop runs `i < n_layer` either way, so it never reaches `blk.24`, `blk.32` or `blk.40` on those files, on any build, stale or current. Those three reported failures cannot be produced by this bug, which is consistent with what [my first comment](https://github.com/unslothai/unsloth/issues/6071#issuecomment-5463081028) found by inspecting the files: the named blocks do not exist in them.

**For anyone landing here from a search** (which is how the OpenWhispr reporter reached this thread): if you see `missing tensor 'blk.N.ssm_conv1d.weight'` on a Qwen3.5/3.6 GGUF that has a NextN/MTP head, meaning its metadata shows `nextn_predict_layers >= 1` and the failing `N` sits in the NextN range at or above `block_count - nextn_predict_layers` (for the usual `nextn_predict_layers = 1` that is simply `block_count - 1`), check `llama-server --version` first. Any build that predates `b9180` (2026-05-16) but is new enough to know the `qwen35` architecture at all, which arrived 2026-02-10, reproduces it on a perfectly good file, whoever quantized it. Older than that and you get an unknown-architecture error instead, not this one. There is no upstream bug left to file. If your file has no NextN head and `N` is not a block it actually contains, that is the separate situation the first comment covers, and updating will not change it.

One small correction to the [closing note](https://github.com/unslothai/unsloth/issues/6071#issuecomment-5681944372), for the record: "the block index in the error is past the model's own block_count" holds for the 0.8B/4B/35B files, but not for the 9B MTP file that actually crashed users, where `blk.32` does exist (`block_count=33`). The conclusion is right, the mechanism is the layer-type misclassification above. On Error Pattern 2 (the `GGML_ASSERT` crash on first inference) I have not re-tested anything, and I want to flag a tension rather than paper over it. Pattern 2 describes a file that *loads* and then asserts. On a pre-`b9180` build an MTP GGUF cannot load at all, since it aborts in `load_arch_tensors`; on `b9180` and later both the guard and `graph_mtp` are present. So no build on either side of that boundary obviously produces "loads fine, crashes on the first prompt". My earlier guess that Pattern 2 was the same staleness does not hold together, and it is better treated as a separate, still-unexplained report.
